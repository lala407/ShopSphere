### P0-1　补「电子邮件确认」闭环（对应要求 #8）— ✅ 已完成（2026-11-15，路线 A）

**已落地的实现**

| 文件 | 作用 |
|---|---|
| `pom.xml` | 新增 `spring-boot-starter-mail` |
| `application.yml` | `spring.mail`（host/port/username/password 全走环境变量，超时 5s）+ `shopsphere.mail.enabled / from-name / base-url` |
| `service/MailService` | 拼中文 HTML 邮件并发送；SENT / FAILED / SKIPPED 三种结果全部落库；任何异常都不外抛 |
| `event/OrderMailEvent` | 值对象（record），只带邮箱/单号/金额/明细，不带实体，避开延迟加载 |
| `listener/OrderMailListener` | `@TransactionalEventListener(AFTER_COMMIT)`：**事务提交后才发信**，回滚不发 |
| `service/MailLogWriter` | `REQUIRES_NEW` 独立事务写 `mail_log`（踩坑点，见下） |
| `entity/MailLog` + `MailLogRepository` | 邮件留痕：类型 / 收件人 / 结果 / 失败原因 / 时间 |
| `OrderService` | 下单、付款、发货三处发布事件 |
| `order-detail.html`、`admin/order-detail.html` | 「邮件通知」区块：已发送至 xxx（时间）/ 未发送（原因）/ 发送失败（原因） |
| `register.html`、`UserService` | 邮箱改为**必填** + 后端正则校验（前端 `required` 可绕过） |
| `docker-compose.yml`、`.env.example` | 新增 `MAIL_*`、`APP_BASE_URL` 注入 |
| `src/test/` | 4 个用例：全链路 + 邮件日志；邮件拼装 / 成功 / 失败（H2 内存库，`mvn test`） |

**发信节点**：下单成功 →「下单成功，请完成付款」；付款 →「付款成功，正在备货」；发货 →「您的订单已发货」。第三封就是 ex.html「付款 → 发送电子邮件确认发货」对应的节点。

**⚠️ 唯一剩余的手工步骤：填 SMTP 授权码**（QQ 邮箱 → 设置 → 账号 → 开启 POP3/SMTP → 生成 16 位授权码），配置 `MAIL_USERNAME` 与 `MAIL_PASSWORD` 两个环境变量（Docker 部署写进 `.env`）。不填也能启动：邮件记 `SKIPPED`，订单照常创建，页面显示「未发送 —— 未配置发件账号」。

**踩坑记录（答辩可讲）**：最初直接在 AFTER_COMMIT 里调 `mailLogRepository.save()`，结果**既不报错也不落库**——此时原事务已结束，线程仍绑着上一个持久化上下文，`persist` 只是把对象放进上下文，永远等不到提交。改用 `MailLogWriter` 的 `REQUIRES_NEW` 开新事务才稳定写入。这个问题是集成测试断言 `mail_log` 行数时才暴露的。

**验证方式**：配好授权码 → 注册带真实邮箱的账号 → 下单（收件箱收到第 1 封）→ 付款（第 2 封）→ 后台发货（第 3 封）；每次订单详情页都会多一行「已发送至 xxx（时间）」。

---

以下保留当初的方案分析，供实验报告「设计思路」一节引用。

ex.html 把「付款 → 发送电子邮件确认发货」写进了主干流程。当时的实现到「点一下模拟付款」就断了，以下两条路线中选择了路线 A（真发信）。

**路线 A（推荐，2–3 小时，能真发信）**
1. `pom.xml` 加 `spring-boot-starter-mail`；
2. `application.yml` 加 `spring.mail`（host/port/username/password 全部用 `${MAIL_PASSWORD:}` 环境变量注入，**不要提交授权码**）；
3. 新建 `service/MailService`：
   - `sendOrderConfirm(Order, User)`：下单/付款后发「订单确认」；
   - `sendShipped(Order, User)`：管理员发货后发「已发货」。
4. **发送时机必须在事务提交之后**：在 `OrderService.createOrder` 末尾直接发信有风险——后面若抛异常回滚，邮件已经发出去了。用 `TransactionSynchronizationManager.registerSynchronization(...afterCommit)` 或 `@TransactionalEventListener(phase = AFTER_COMMIT)`。
5. 发信失败要 `try-catch` 吞掉并 `log.warn`，**绝不能因为 SMTP 挂了导致下单失败**。
6. 注册时把邮箱改成**必填**（现在 `register.html` 是「邮箱（选填）」，`UserService` 也不校验格式），否则一半用户根本收不到邮件。
7. 订单详情页显示一行「确认邮件已发送至 xxx@xx」，让老师不登录邮箱也能看到证据。

**路线 B（兜底，30 分钟，只做可演示）**
- 不接 SMTP，在 `OrderService.pay/ship` 里 `log.info("[邮件] 订单 {} 已确认，收件人 {}", ...)`；
- 同时把「邮件已发送至 xxx」写进订单详情页 + 建 `mail_log` 表留痕；
- 报告里明确写「模拟邮件，未接真实 SMTP」，并在截图里给出日志行。

> 判定标准：老师点「付款」后，要么收到真邮件，要么能在页面上看到「已发送至某邮箱」的痕迹。两者都没有 = 这条需求算未实现。

**采集规则（唯一规则表，集中在一处）**

| 动作 | 触发 | 目标 |
|---|---|---|
| `VIEW_LIST` 浏览列表 | `GET /` | — |
| `VIEW_PRODUCT` 查看商品 | `GET /product/{id}` | PRODUCT #{id} |
| `ADD_CART` 加入购物车 | `POST /cart/add` | CART #{productId} |
| `CREATE_ORDER` 提交订单 | `POST /order/create` | —（订单号此刻还没生成） |

1. 游客访问 `/` 与 `/product/20` → 2 条记录，`user_id` 为 NULL，`ip=::1`、`ua=curl/8.21.0`；
2. 登录用户加购 19 号商品 → 下单（订单 9）→ 付款 → 3 条记录，`user_id=5`，`PAY_ORDER` 的 `target_id=9`；
3. `/admin/log` 页面：今日新增 5 条，5 个动作各 1 次；按「查看商品」筛选后只剩 1 条且条件回显；
4. `mvn test` 8 个用例全绿。

**踩坑记录**：模板里写 `${counts[a]}`（`Map<AccessAction,Long>`）会抛
`IllegalArgumentException: The target type java.lang.Enum does not refer to an enum`。
改成在 Controller 里转成 `Map<String,Long>`（键为枚举名）、模板写 `${counts[a.name()]}` 才正常 —— 这个坑只有真渲染页面才会暴露，单测不跑模板就发现不了。
