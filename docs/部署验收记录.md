## 3. 服务器上要执行的命令（清单第 1、3 项收口用）

在服务器仓库目录执行（**`down` 千万不要加 `-v`**，加 `-v` 会连 `mysql-data` 卷一起删，那就成了"数据不持久"的反面教材）：

```bash
cd /path/to/ShopSphere        # 换成仓库实际路径，例如 /root/ShopSphere
docker compose ps             # 期望两行：shopsphere-app / shopsphere-mysql，状态 Up
docker compose down           # 不加 -v：保留 mysql-data 卷
docker compose up -d
docker compose ps             # 再次确认两个容器 Up
curl -s http://127.0.0.1:8080/healthz
```

执行完回公网页面看订单是否还在（`demo` 登录 → `/orders`，应能看到 `ORD20261116200749837771029` 与 11-15 的历史单）。把 `docker compose ps` 的终端输出截图或粘贴回来，第 1、3 项即可从 ⏳/⚠️ 改成 ✅。

## 5. 容易被问到的两个点

- **为什么服务能打开就算"容器在跑"不能算数？** 不能算。#1 要的是"容器编排确实按 compose 起了两个独立容器"，只有 `docker compose ps` 能证明；外部 HTTP 只能证明"有个能用的服务"（可能是 `java -jar` 直接跑的）。
- **持久化怎么一眼看出来？** 看 `docker-compose.yml` 里 `mysql-data:/var/lib/mysql` 这行 + 截图 08 里的 11-15 历史单：数据在容器重建后还在，说明写的是卷不是容器可写层。

## 6. 附：后台「分类管理」「统计报表」打不开的排查记录（2026-11-16 20:47）

**现象**：本地 `http://localhost:8080` 后台点「分类管理」返回 404（页面显示"页面不存在"），点「统计报表」返回 500（"服务器开小差"），而「商品管理」「订单管理」「访问日志」和前台全部正常。

**排查**（三步定位，全程没有改一行业务代码）：

1. 看导航：后台导航里已经有「分类管理」页签——说明 **模板是新的**（`admin-nav.html` 的改动生效了）。
2. 但该页签点进去 404：说明 **Controller 里没有 `/admin/category` 这个映射**，即 **class 是旧的**。一个进程里同时存在新模板和旧 class，只有一种可能：**应用启动在前、代码更新在后**。
3. 验证代码本身没问题：把当前源码重新打 jar，分别在 8085（dev profile）和 8086（prod profile + 全新库）起两个实例，`/admin/category` `/admin/stats` 等五个后台页全部 200。既然新构建一切正常，问题就锁定在"跑着的那个进程"。

**根因**：本地这个实例是 16:14 用 `mvn spring-boot:run` 起的，晚上 18:00 之后代码又加了 P1-8（分类管理）、P1-9（统计报表重做）。`application.yml` 里 `thymeleaf.cache: false`，模板每次请求都重新读文件 → 导航立刻变新；而 JVM 里的类加载器不会因为源文件变了就换实现 → 新页面没有接口（404）、统计页新模板拿不到新 model 属性（500）。

**修复**：停掉旧进程，用最新构建重启。

```
# 本地
# 1) 结束占着 8080 的旧 java 进程  2) 重新启动（会重新编译）
.\scripts\run-local.ps1
# 服务器（镜像里模板和 class 同源，不会错配）
docker compose up -d --build
```

**结果**：本地五个后台页全部 200，截图 `10-修复后-分类管理.png`、`11-修复后-统计报表.png`（统计页的每日条形图 / 分类占比 / Top5 均正常出数）。

**给验收的一句话**：这类"半新半旧"是 Java 项目最典型的假故障——**模板热、类不热**。判断方法就一条：导航里有新入口但点进去 404，几乎一定是没重启；镜像部署不会有这个问题，因为 docker build 每次都整包重编译。

## 7. 收口：容器重建实测（清单第 1、3 项）

**背景**：11-16 21:00 前后在本地排查后台 404/500 时，服务器上的容器被 `down` 掉了（没带 `-v`，卷保留），但 `up` 没有真正跑起来 —— 于是出现了一段"机器活着、应用没起"的窗口。这段意外停机，恰好成了第 3 条最真实的现场。

### 7.1 停机窗口（反证：服务确实停过）

```
# 21:10–21:17 公网连续探测，全部连不上
21:15:56 healthz=000   21:16:10 healthz=000   21:16:23 healthz=000
21:16:36 healthz=000   21:16:49 healthz=000   21:17:03 healthz=000

# 同一时刻端口探测：22 / 80 通，8080 关
22 open     80 open     8080 closed

# 容器已不存在（compose 视角全空）
[root@VM-0-11-opencloudos ShopSphere]# docker compose ps -a
NAME      IMAGE     COMMAND   SERVICE   CREATED   STATUS    PORTS
```

`ps -a` 一条都没有 → 不是"容器崩了在重启"，而是**容器被删掉了**。这是最严格的 down 场景：连容器都不存在，只剩命名卷。

### 7.2 重建（卷接上，数据原样回来）

```
[root@VM-0-11-opencloudos ShopSphere]# docker volume ls | grep -i mysql-data
local     shopsphere_mysql-data          # 卷还在 —— down 没带 -v 的关键
[root@VM-0-11-opencloudos ShopSphere]# docker compose up -d
[+] up 2/2
✔ Container shopsphere-app     Running
✔ Container shopsphere-mysql   Healthy
[root@VM-0-11-opencloudos ShopSphere]# docker compose ps
NAME               IMAGE            SERVICE   CREATED         STATUS                   PORTS
shopsphere-app     shopsphere-app   app       4 minutes ago   Up 4 minutes             0.0.0.0:8080->8080/tcp
shopsphere-mysql   mysql:8.0        mysql     4 minutes ago   Up 4 minutes (healthy)   3306/tcp, 33060/tcp
[root@VM-0-11-opencloudos ShopSphere]# curl -s http://127.0.0.1:8080/healthz
UP db=12ms
```

注意 `CREATED 4 minutes ago` —— 容器是**新造的**，不是复用旧容器。所以后面看到的订单，只能来自 `mysql-data` 卷。

### 7.4 复盘：这次为什么停了半小时

`down` 执行成功（容器和网络都被清掉），但后续 `up -d` 没有真正跑起来。`docker images` 里 `shopsphere-app:latest`（550MB）一直在，所以不是镜像丢了，是**命令没跑或跑到一半被打断**。

**教训（也是可以写进答辩的一句话）**：`down` 与 `up` 必须成对执行，中间别插别的操作；`down` 不加 `-v` 数据是安全的，但服务会一直不可用 —— 这是"在线部署"这项最典型的失分方式：**代码没问题、镜像也没问题，只是容器没起**。日常巡检一条命令足够：`docker compose ps` 看到两行 Up 才算线上活着，`/healthz` 返回 `UP` 才算数据库也通。
